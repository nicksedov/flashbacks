# Design

## Context

Face recognition already produces people (`domain.Person`) and faces
(`domain.Face`, `personId` 0 when unassigned), exposes them through
`GET /api/people`, `GET /api/people/:id/photos` and `GET /api/image-faces`, and
renders them in the workspace People tab and in the lightbox People mode. Every
existing face endpoint is read-only.

Two pieces of current behavior shape this work:

- The recognition job re-derives people on every pass: `clusterAssign` only
  loads faces with `person_id = 0`, `reconcilePeople` merges people whose
  medoids are close, and `resetGeneratedPeople` deletes every person whose
  `name` is empty when `ReclusterAll` is set. Anything the user curates must be
  invisible to those three paths, or it will be undone on the next scheduled
  pass.
- `people.Store` today infers "generated by the job" from an empty name, and
  `peopleHide` in the listing hides people with zero photos. An inferred
  heuristic cannot express "the user created this unnamed person from three
  faces", so the state needs an explicit flag.

See [proposal.md](proposal.md) for motivation and
[specs/](specs/) for the behavioral contract.

## Goals / Non-Goals

**Goals:**

- One transactional application service owns every catalog mutation, so a
  merge/disband cannot leave faces, people, covers and exemplars inconsistent.
- A durable, explicit notion of "the user decided this" that the background job
  reads instead of guessing from names.
- The same operations reachable from both People surfaces, with the lightbox
  limited to what makes sense on one photo.

**Non-Goals:**

- No change to detection, embedding, thresholds or the clustering algorithm's
  matching rules.
- No automatic merge suggestions or similarity display in the UI.
- No face-crop generation; unassigned faces reuse photo thumbnails.
- No bulk "forget all manual decisions" action (see Open Questions).
- No per-user ownership of the catalog; it stays shared library state.

## Decisions

### 1. Manual state is persisted on the rows

Add `Person.Manual bool` (`gorm:"not null;default:false"`) and
`Face.ManualAssignment bool` (`gorm:"not null;default:false;index"`).

| Action | Persisted effect |
|---|---|
| rename a person | `people.manual = true` |
| merge people | target `manual = true`; every face of target and sources gets `manual_assignment = true` |
| create a person from faces | new person `manual = true`; its faces `manual_assignment = true` |
| assign a face to a person | face `manual_assignment = true` |
| detach a face | face `person_id = 0`, `manual_assignment = true` |
| disband a person | its faces `person_id = 0`, `manual_assignment = true`; person row and its exemplars deleted |

The job then changes in exactly three places:
`clusterAssign` loads `person_id = 0 AND manual_assignment = false`;
`reconcileRound` skips people with `manual = true` (neither merged away nor
merged into); `resetGeneratedPeople` deletes `manual = false` people instead of
`name = ''` people.

*Alternative considered:* keep inferring manual state from a non-empty name and
extend it to "has a name or was created by the user" — rejected because an
unnamed person created from unassigned faces is still a user decision, and the
name-based rule would have to be re-guessed at every pass.

*Consequence:* a curated person is no longer auto-merged with an automatic
cluster of the same identity. That is intentional: the user asked for control,
and the merge action is always available in the People tab.

### 2. Mutations live in a new `application/people` catalog service

Create `backend/core/internal/application/people/catalog.go` holding a
`Catalog` struct with `db *gorm.DB`, `PersonRepository`, `FaceRepository`,
`PersonReferenceRepository` (optional) and `ImageFileRepository`. Each mutation
is one `db.Transaction` (pattern already used in
`application/agent/conversation_service.go`); handlers only parse input, map
domain errors to status codes and build DTOs.

*Alternatives considered:* putting the logic in the Gin handlers (current style
for reads) — rejected because merge/disband span four tables and would put
transaction management into the transport layer; adding one GORM method per
operation — rejected because it hides business rules inside the repository and
makes SQLite-in-memory tests slower to write.

Repository additions stay small and generic: `FaceRepository` gains
`ListUnassigned(offset, limit int) ([]domain.Face, error)` and
`CountUnassigned() (int64, error)`; `PersonRepository` gains `Delete(id uint)
error`. Merge/detach reuse `PersonReferenceRepository.List`, `Replace` and
`DeleteByPersonIDs`.

### 3. Reference exemplars follow the edit

- **Merge:** read the target and source reference sets with `List`, concatenate
  them (target first, duplicates by face id removed, capped at the existing
  `exemplarLimit` of 5), `Replace` the target's set, then
  `DeleteByPersonIDs(sources)`. A later pass therefore recognises a source
  identity as the merged person.
- **Detach:** `List` the person's references, drop the detached face, `Replace`
  the remaining set.
- **Disband:** `DeleteByPersonIDs([]uint{id})`.
- **Create from faces:** build the new person's exemplars from the assigned
  faces' embeddings, reusing the same selection rule as the job (highest
  quality per distinct image, up to 5).

Covers follow the same rule: merge keeps the target's cover and falls back to
the first source cover; detach of a cover face promotes the person's lowest-id
remaining face; disband leaves nothing behind.

### 4. API surface

All paths join the existing authenticated face-recognition block in
`router.go`; CSRF applies to the non-GET verbs exactly as for other mutations.

| Method & path | Body | Response |
|---|---|---|
| `PATCH /api/people/:id` | `{ "name": string }` | `PersonDTO` |
| `POST /api/people` | `{ "name"?: string, "faceIds": number[] }` | `PersonDTO` (201) |
| `POST /api/people/merge` | `{ "targetPersonId": number, "sourcePersonIds": number[], "name"?: string }` | `PersonDTO` |
| `DELETE /api/people/:id` | — | `{ "message": string }` |
| `PATCH /api/faces/:id` | `{ "personId": number }` | `ImageFaceDTO` |
| `GET /api/faces/unassigned?page=&pageSize=` | — | `UnassignedFacesResponse` |

Validation: names are trimmed and limited to 200 characters (no uniqueness
constraint — two people may share a name until the user merges them);
`faceIds` holds 1–200 distinct ids; `sourcePersonIds` holds 1–50 distinct ids
and must not contain the target; unknown ids answer 404 and leave the database
untouched; a `personId` of 0 on `PATCH /api/faces/:id` detaches.

`UnassignedFaceDTO` reuses the box/confidence fields of `ImageFaceDTO` and adds
`path` and `fileName` for the thumbnail; the listing joins `image_files` so
faces of vanished photos are excluded, and mirrors the pagination envelope of
`PersonPhotosResponse` (`totalFaces`, `currentPage`, `pageSize`, `totalPages`,
`hasNextPage`). `docs/api-contracts/core.yaml` gains these paths and schemas;
`make generate-types` regenerates `webapp/src/types/api.ts`.

### 5. Screens and interaction split

| Screen | Catalog actions |
|---|---|
| Workspace → People tab (grid) | search by name, multi-select merge, rename, disband (with confirmation) |
| Workspace → People tab → person detail | rename, disband, open photos |
| Workspace → People tab → Unassigned faces | select faces, attach to an existing person, create a new named person |
| Unified lightbox → People tab | rename a person, select a face box, reassign it to another person, detach it, attach an unnumbered face |

The lightbox deliberately has no merge/disband: those are catalog-level
decisions, and the People tab is the screen that shows the whole catalog.

New webapp pieces:

- `PeopleTab.tsx` becomes the catalog screen: keeps `people`, a selection set,
  the search text, and toggles between grid, detail and unassigned views.
- `UnassignedFacesView.tsx` — paginated grid of photo thumbnails with the face
  box drawn over each, selectable; mirrors `PeopleImagePanel`'s scaling
  (`box * renderedSize / naturalSize`).
- Shared dialogs built on the existing dialog primitive:
  `RenamePersonDialog`, `MergePeopleDialog` (resulting name + distinct photo
  count preview), `DisbandPersonDialog` (states that photos are kept),
  `PersonPickerDialog` (searchable people list + "create new person" with a
  name field). The picker always lists the whole catalog, not only the people
  already on the opened photo, so a face can be moved to a person who is not
  present on it.
- `PeoplePanel.tsx` gains `onRename(personId)`; `PeopleImagePanel.tsx` turns each
  box into a focusable button (`pointer-events-auto` inside the existing
  `pointer-events-none` overlay, `aria-label` naming the face) and reports the
  selected face. Selecting a face opens the face action dialog with
  "assign to person…" and, for an assigned face, "this is not <person>"; the
  same dialog can create a new named person from an unassigned face.
- `useImageFaces` gains `refresh()`, driven by a nonce in the fetch effect, so a
  correction re-reads the photo without closing the lightbox.
- `endpoints.ts` gains `renamePerson`, `mergePeople`, `createPerson`,
  `disbandPerson`, `assignFaceToPerson`, `fetchUnassignedFaces`.

### 6. Presentation and localization rules

- Dialog surfaces, selectable tiles and destructive buttons follow
  `openspec/specs/design-system/spec.md`; the disband action uses the
  destructive variant and never fires from a single tap.
- Every interactive element keeps the 44×44 minimum touch target; selected
  tiles and selected faces expose `aria-pressed`/`aria-selected`.
- All new labels, dialog copy, confirmations and empty states are added to
  `translations.en.ts` and `translations.ru.ts` in the same change; the
  localized "Person N" placeholder stays the label for unnamed people.
- Errors from mutations surface through the existing toast helper; a failed
  merge or disband leaves the current view unchanged.

### 7. Tests

- Go: table tests for the catalog service on in-memory SQLite (rename trim and
  clear, merge unions faces and counts distinct photos, disband keeps photos,
  detach/assign lock flags, unknown ids), handler tests for status codes and
  DTO shape, and job tests proving a manual person is not reconciled and a
  locked face is not re-clustered.
- Webapp: Vitest for the grid tools (search, selection, merge availability),
  each dialog's confirm/cancel path, the unassigned view attach/create flows,
  and the lightbox correction flow refreshing boxes and the people list.
- End-to-end: a Playwright suite in `tests/e2e/` replaces the manual
  four-screen walkthrough and runs the real webapp against a live deployment.

### 8. Browser automation replaces the manual walkthrough

The catalog is only correct when the four screens work together over real HTTP
and a real browser. The manual walkthrough is therefore an executable Playwright
suite, committed with the change:

- **Headless on the server by default.** `npm run test:e2e` launches Chromium in
  the code-server environment; no local browser is required and the same command
  works on CI.
- **Optional local browser via `@rushstack/playwright-browser-tunnel`.**
  `PW_TUNNEL=1 npm run test:e2e:tunnel` swaps the `browser` fixture for a
  tunneled browser: the developer runs `tests/e2e/browser-host.cjs` on their own
  machine and forwards tunnel port `56767` to the server, so they can watch the
  run locally while the tests execute remotely.
- **The target is a live deployment.** `E2E_BASE_URL` defaults to
  `https://staging.flashbacks.life`; the suite is not tied to a local dev server.
- **Credentials are environment input.** `E2E_LOGIN` / `E2E_PASSWORD` must be
  set (staging admin). Without them every spec skips with an explicit reason
  instead of failing, so a checkout without secrets stays green.
- **Seeding is API-driven and self-cleaning.** Specs create throwaway people
  from unassigned faces through the catalog endpoints, drive the UI, and disband
  what they created in `afterAll`. Existing people are never modified. A
  gallery without enough unassigned faces makes the face-dependent spec skip.
- **Deterministic selectors and language.** Tests use the `data-slot` /
  `data-testid` hooks the UI already exposes and force the interface language to
  English through `PUT /api/user-settings` for the run, restoring the previous
  setting afterwards.

*Alternative considered:* recording the manual walkthrough as a checklist in the
tasks file — rejected because it neither proves the shipped build nor protects
the scenarios from regressions.

## Risks / Trade-offs

- **Curated people stop being auto-enriched** → documented in the proposal and
  the People tab copy; the merge action is one click away.
- **The manual flag is sticky** → a wrong correction locks a face until the user
  fixes it; the same dialogs allow reassigning or detaching again at any time.
- **Merge transactions on a large gallery** → per-statement batches of 500 face
  rows, the 50-source cap and a single transaction keep the write bounded; the
  photo counts and listing are computed after commit.
- **AutoMigrate adds columns to a live table** → both columns are
  `not null default false`, so existing rows are valid and no backfill is
  needed; the change is additive and reversible by reverting the code.
- **`resetGeneratedPeople` semantics change** → it now deletes only
  `manual = false` people. Today no person has a name and no manual flag, so a
  full re-cluster behaves exactly as before; after this change a user-created
  unnamed person survives, which is the intent.
- **Duplicate names** → allowed by design; the tile shows the photo count so the
  user can tell the people apart before merging. A unique constraint would make
  the merge-first workflow impossible.
- **Face clicks versus image gestures** → only People mode enables pointer
  events on boxes, so pan/zoom behavior in the other modes is untouched.

## Migration Plan

1. Ship the domain columns and the job filters together: until the job stops
   touching manual rows, a scheduled pass would undo user edits within the
   schedule window.
2. `AutoMigrate` (both Postgres and the SQLite test DB) adds `people.manual` and
   `faces.manual_assignment` with defaults, so no data migration is required.
3. Deploy core first (API + job), then the webapp build; the endpoints are
   additive and the old webapp keeps working.
4. Rollback: revert the webapp, then core. The two columns stay but are ignored
   by the reverted code; no stored faces or people are lost. Manual edits made
   before a rollback become ordinary generated state again.

## Open Questions

- Do we need an explicit "forget all manual decisions" control (per person or
  globally) so `ReclusterAll` can rebuild a catalog the user has heavily
  curated? It does not change any requirement or the approach, so it can be
  decided after first use.
